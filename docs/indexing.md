# Indexing the `memberships` table

Working notes from tuning `GET /organisations`. Records what was measured, on what
data, and what the numbers actually mean — including the places the measurements
lied.

---

## 1. Why this table

`memberships` is the only join table on the hot path. Every org-scoped request
touches it, and it is the one table where a missing index turns into a full scan:

- it is filtered by `user_uid` alone (list a user's organisations),
- by `org_uid` alone (list an org's members),
- and by both (permission checks).

`organisations` and `users` are only ever reached by `uid`, which is already
unique-indexed, so nothing extra is needed there.

## 2. Schema and the indexes you get for free

```sql
create table if not exists memberships (
    id serial primary key,
    uid uuid unique not null,
    created_at timestamptz default now(),
    updated_at timestamptz default now(),
    org_uid uuid not null,
    user_uid uuid not null,
    role varchar(16) not null,
    unique(org_uid, user_uid)
)
```

Three indexes come from constraints and cannot be dropped independently of them:

| index | columns | source |
|---|---|---|
| `memberships_pkey` | `(id)` | `primary key` |
| `memberships_uid_key` | `(uid)` | `uid ... unique` |
| `memberships_org_uid_user_uid_key` | `(org_uid, user_uid)` | `unique(org_uid, user_uid)` |

Anything beyond these is a deliberate choice.

## 3. Query shapes in the codebase

Indexes are chosen from the queries, not from plans you happen to like. These are
every shape the app issues against `memberships`:

| caller | predicate | order by | served by |
|---|---|---|---|
| `_get_role` | `org_uid = $1 and user_uid = $2` | — | `unique(org_uid, user_uid)` |
| `list_members` | `org_uid = $1` | — | same (org leads) |
| `create_members` (insert) | — (unique check) | — | same |
| `delete_member` | `org_uid = $1 and user_uid = $2` | — | same |
| `update_member_role` | `user_uid = $2 and org_uid = $3` | — | same |
| `list_organisations` | `user_uid = $1` | `o.id` / `m.id` | **needs a user-leading index** |

The unique constraint covers five of the six for free. Only
`list_organisations` needs anything added — the constraint's index is
**org-leading**, and a btree on `(org_uid, user_uid)` cannot serve
`where user_uid = ?` because the matching entries are scattered across every
`org_uid` value with no contiguous range to seek to.

## 4. Column-order rule

**Equality → Sort → Range.** Columns compared with `=` go first (order among them
does not matter), then the `ORDER BY` column, then any range predicate. Once a
column is used for a range, nothing after it in the index can serve sorting.

**Prefix rule.** An index on `(a, b)` already serves `where a = ?`. A separate
`(a)` is dead weight — write amplification for no new access path.

## 5. Experiments

### Setup

`python seed.py` → 10,000 users, 10,000 organisations, 20,200 memberships
(10,000 owner rows + 10,200 member rows), followed by `ANALYZE`.

A probe user, `probe@seed.local`, is placed in 200 organisations so the list
endpoint has something to paginate.

> **Seed caveat that distorted several plans below.** `seed.py` assigns the probe
> user to orgs `0..199` **sequentially**, so its organisations are the *lowest*
> `id`s in the table. Any plan that walks `organisations` in `id` order therefore
> finds matches immediately. See experiment 4.

### Experiment 1 — no user-leading index

```sql
select m.org_uid, m.user_uid from organisations o
join memberships m on o.uid = m.org_uid
where m.user_uid = '<uid>' limit 10;
```

```
Seq Scan on memberships m  (actual time=1.557..1.557 rows=0 loops=1)
  Filter: (user_uid = '...'::uuid)
  Rows Removed by Filter: 20200
Execution Time: 1.582 ms
```

`user_uid` appears as **`Filter:`**, not `Index Cond:` — the definitive signal
that no index could be used. All 20,200 rows were read and discarded.

### Experiment 2 — add `memberships(user_uid)`

```sql
create index memberships_user_uid_idx on memberships(user_uid);
```

```
Bitmap Heap Scan on memberships m
  Recheck Cond: (user_uid = '...'::uuid)
  ->  Bitmap Index Scan on memberships_user_uid_idx
        Index Cond: (user_uid = '...'::uuid)
Execution Time: 0.036 ms
```

`Filter` became `Index Cond`. **But this measurement is worthless on its own** —
the uid used had been generated by an earlier seed run and matched **zero** rows.
`rows=0` on every node, and the organisations side reports `never executed`.
0.036 ms is the cost of finding nothing.

**Lesson: always confirm your test value exists.** The `rows=2` estimate is the
planner's default guess for a value absent from the statistics.

### Experiment 3 — the row estimate picks the plan, not the `ORDER BY`

Identical SQL (`... order by o.id asc limit 10`), two different uids:

| uid | est. rows | actual | access path | sort? | time |
|---|---|---|---|---|---|
| stale (absent) | 2 | 0 | `memberships_user_uid_idx` → join | Sort | 0.067 ms |
| probe | 202 | 202 | `organisations_pkey` walk → `memberships_org_uid_user_uid_key` (Index Only) | none | 0.092 ms |

Two legitimate strategies:

- **(a) org-driven** — walk `organisations` already in `id` order and probe
  memberships per row. No sort, but it examines orgs the user does not belong to.
- **(b) membership-driven** — fetch all the user's memberships, join, then sort.
  Cost scales with that user's org count, not with table size.

Postgres picks by estimated selectivity. Both indexes are load-bearing; neither
is redundant.

A normal seeded user (3 orgs, ids spread 303–9788) gets plan (b):

```
Sort (Sort Key: o.id, quicksort, 25kB)
  ->  Nested Loop
        ->  Bitmap Heap Scan on memberships m
              ->  Bitmap Index Scan on memberships_user_uid_idx
        ->  Index Scan using organisations_uid_key on organisations o
Execution Time: 0.112 ms
```

### Experiment 4 — the deep-page pathology of plan (a)

Same query, same indexes, only the cursor position changes:

| cursor | rows returned | org rows walked | buffers | time |
|---|---|---|---|---|
| `o.id > 0` | 10 | 10 | 24 | **0.104 ms** |
| `o.id > 200` | 2 | 9,800 | 19,732 | **11.0 ms** |

**100× slower, 19,732 buffers to return 2 rows.** 9,800 index probes, nearly all
returning nothing.

Page 1 is fast *only* because of the seed artifact — probe's orgs are ids 1–200.
Any user whose organisations sit further into the id range hits this on **page
one**. The cost estimate admitted it: `Nested Loop (cost=0.57..4131.20 rows=202)`
expects ~500 organisations examined per 10 matches (202/10,000 ≈ 2% hit rate);
it actually examined 10.

This cannot be fixed with an index on `organisations`. The discarded rows are
legitimately in the table — they are simply not this user's. The selectivity
lives in `memberships` while the sort key lives in `organisations`, and
**an `ORDER BY` cannot be indexed across a join**.

### Experiment 5 — move the sort key to the membership

```sql
create index memberships_user_uid_id_idx on memberships(user_uid, id);
```

```sql
select o.*, m.role from memberships m
join organisations o on o.uid = m.org_uid
where m.user_uid = $1 and m.id > $2
order by m.id asc limit $3
```

```
Limit (actual time=0.161..0.185 rows=10 loops=1)
  Buffers: shared hit=24
  ->  Nested Loop
        ->  Index Scan using memberships_user_uid_id_idx on memberships m
              Index Cond: ((user_uid = '...'::uuid) AND (id > 10009))
        ->  Index Only Scan using organisations_uid_key on organisations o (loops=10)
              Heap Fetches: 0
Execution Time: 0.199 ms
```

Same page as the 11.0 ms case above: **11.19 ms → 0.199 ms, 19,732 → 24 buffers**,
and it returns a full page of 10 instead of 2.

One index seek serves both the filter and the ordering, then exactly `limit`
primary-key lookups. Page 200 costs the same as page 1.

**The nested loop was never the problem.** With `LIMIT 10` a nested loop is
correct — a hash join would build a hash over 10,000 organisations to return 10
rows. What changed is the **loop count**: `loops=9800` → `loops=10`.

Trade-offs: the cursor becomes a membership id, and ordering becomes "when the
user joined" rather than "when the org was created".

### Experiment 6 — keeping org-centric ordering

If ordering by an `organisations` column matters, force plan (b) with a
materialized CTE so the planner cannot flip back to the org-driven walk:

```sql
with mine as materialized (
    select org_uid, role from memberships where user_uid = $1
)
select o.*, mine.role from mine
join organisations o on o.uid = mine.org_uid
order by o.name asc limit 10 offset $2
```

110 buffers at offset 190, versus 19,732 for the org-driven plan. `as materialized`
is load-bearing — without it Postgres inlines the CTE and may revert to plan (a).

Cost is proportional to that user's membership count, so this is fine while users
belong to tens of organisations, not thousands.

### Benchmark

30 iterations each, timed client-side after a warm-up. `EXPLAIN ANALYZE`'s own
per-node instrumentation is not reliable here — it reported 16 ms for a query
touching 110 buffers.

| query | median | p95 |
|---|---|---|
| `order by o.id` (deep page) | 1.119 ms | **11.431 ms** |
| `order by m.id` (keyset on membership) | 0.801 ms | **0.955 ms** |
| materialized CTE, `order by o.name`, offset 190 | 1.386 ms | 2.609 ms |

The medians are close because everything is cached. **The p95 spread is the
signal** — only the `m.id` version is flat.

## 6. Current state

`db.py` creates one index beyond the constraints:

```python
await conn.execute(
    "create index if not exists memberships_user_uid_id_idx on memberships(user_uid, id)"
)
```

**Open item:** `list_organisations` still issues `order by o.id` with a cursor on
`o.id`, so it does **not** use `(user_uid, id)` for ordering — it gets plan (a) or
(b) depending on selectivity, and remains exposed to the experiment 4 pathology.
Either switch the query to `order by m.id` (experiment 5) or change the index to
`(user_uid, org_uid)` to at least make the membership probe index-only.

## 7. Pitfalls hit along the way

**`create index if not exists` matches on name, not definition.** Retrying with a
different name silently creates a duplicate. At one point `memberships` carried
seven indexes, three of them identical copies of `(org_uid, user_uid)`. Every one
is maintained on every write.

**Editing `db.py` does not remove anything.** `create ... if not exists` only ever
adds. An index dropped from the file survives in the database until dropped by
hand. There are no migrations in this project yet — the same trap applies to
column changes, where `create table if not exists` is a silent no-op against an
existing table.

**Naming.** An index called `organisations_user_uid_idx` that lives on
`memberships` will confuse everyone reading `\di` later. Match the constraint
convention: `<table>_<columns>_idx`.

**Measure distribution, not just volume.** 10,000 rows fit entirely in shared
buffers — `Buffers: shared hit=…` with zero reads — so these numbers compare CPU,
not I/O. And the probe user's sequential org ids flattered every org-driven plan.
Seed at least an order of magnitude larger, with realistic scatter, before
trusting a plan comparison.

## 8. Checklist

1. Write down the query shapes. Do not start from a plan.
2. Equality columns first, then `ORDER BY`, then range.
3. Drop any index that is a prefix of another.
4. Verify with `EXPLAIN (ANALYZE, BUFFERS)` on realistic data:
   - `Filter:` where you expected `Index Cond:` → the index is not usable
   - `Seq Scan` on a table you meant to seek into
   - `loops=` on the inner side far exceeding your `LIMIT`
   - `Rows Removed by Filter` in the thousands
5. Time it client-side at p95, not by reading `Execution Time` off one run.
6. `ANALYZE` after bulk loading, or the planner works from stale statistics.
